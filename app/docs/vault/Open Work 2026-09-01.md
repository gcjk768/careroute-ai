## 1. Red-flag case hangs in the browser — RESOLVED 2026-09-02

**Root cause (measured, not inferred).** The browser reaches `/api/triage/stream` through the Next.js
`/api` rewrite. Next proxies rewrites with `http-proxy` and a default **`proxyTimeout` of 30 s**
(`next/dist/server/lib/router-utils/proxy-request.js`). That timeout is an *idle* timeout on the
upstream socket: when the backend sends no bytes for 30 s the proxy aborts the upstream request but
**never ends the browser's response**, so the page sees neither data nor an error — exactly the
`ERR_NETWORK_IO_SUSPENDED`-shaped silence in the traces. Direct to `:8000` the same stream survives
the gap in Chrome, which is why every backend-side check looked innocent.

Measured from inside Chrome with a synthetic SSE server behind a throwaway Next rewrite:

| Silent gap | Result |
|---|---|
| 20 s, 26 s | delivered in full |
| 32 s, 40 s | **stalls forever** (no close, no error) |
| 40 s + `: keepalive` comment every 10 s | delivered in full |

The red-flag path gaps ~30 s on the LLM; after the OneMap failsafe merge, Care Routing's shortlist +
bounded replan gaps 24-40 s on OneMap. Both sit on or over the edge, which is why the P4 clinic path
hung intermittently and the public-transport path hung reliably.

**Fix.** `app/main.py` wraps the orchestrator generator in `_with_heartbeat`, which emits an SSE
comment frame (`: keepalive`) whenever the pipeline has been silent for
`CAREROUTE_SSE_HEARTBEAT_SECONDS` (default 10 s, 3x margin under Next's 30 s). Comment frames carry
no `data:` line, so `lib/api.js` and `parse_sse` already ignore them; they exist only to reset idle
timers between the backend and the browser. Verified in Chrome through the real proxy: public-transport
case, 24/24 events, `final` at 49.5 s across a 39 s routing gap. Tests: `tests/test_sse_heartbeat.py`.

**Why not `experimental.proxyTimeout` in `next.config.mjs` instead?** It only moves the number, and
only for Next. Any reverse proxy in front of the backend (nginx, a cloud load balancer) has its own
idle timeout; a heartbeat defeats all of them. Raising `proxyTimeout` as well is harmless belt-and-braces
if anyone wants it.

**Note for the e2e suite.** The three "failing on purpose" red-flag specs should now pass. The
anti-throttling Chrome flags in `playwright.config.js` were never the cause and can stay or go.

> [!warning] Measurement lesson worth keeping
> compression was "ruled out" early by comparing `curl` with and without `--compressed` — both returned
> 27/27, so it looked innocent. That test *cannot* detect the fault: curl waits for the whole body
> regardless, so a fully buffered response still yields every event. The same instrument problem hid
> the proxy timeout: curl through the proxy also "worked" because curl never went idle the way a
> browser fetch does. Measure the thing you actually care about — chunk arrival times, in a browser.

## 5. Git TLS verification is disabled — one fix unblocks three things

`http.sslVerify=false`, so every fetch/push prints a security warning and is not authenticated against
a MITM. It is also why `npx playwright install` fails with `SELF_SIGNED_CERT_IN_CHAIN`, and why the CI
e2e job has to use a pre-baked browser image.

```bash
# get the proxy's root CA from Windows cert store or IT, then:
git config --global http.sslCAInfo "C:/path/to/corp-root-ca.pem"
git config --global --unset http.sslVerify
setx NODE_EXTRA_CA_CERTS "C:\path\to\corp-root-ca.pem"
```

One certificate fixes git, npm and Playwright downloads together.
